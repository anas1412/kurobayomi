## 1. Purpose and scope

### 1.1 What Aniyomi does here (OBSERVED)

- Aniyomi keeps the entire manga side of the app in one SQLite file, `tachiyomi.db`, created by `AndroidSqliteDriver` in `app/src/main/java/eu/kanade/tachiyomi/di/AppModule.kt:78-101`. The anime side is a second file, `tachiyomi.animedb`, owned by [area:04-db-anime-schema-migrations](../04-db-anime-schema-migrations/).
- Schema is generated by SQLDelight 2.0.2 from the `.sq` files (`data/build.gradle.kts`, dialect `sqlite-3-38-dialect`, package `tachiyomi.data`, generated class `Database`). `Database.Schema.version` is 33 because the highest migration is `migrations/32.sqm`.
- The database holds: library entries (`mangas`), chapters, library categories and their links, read history, tracker bindings (`manga_sync`), per-entry excluded scanlators, remembered stub sources, extension repositories, plus three views (`libraryView`, `historyView`, `updatesView`) that the UI and backup code read.
- Sync and backup bookkeeping (`version`, `last_modified_at`, `favorite_modified_at`, `is_syncing`) is maintained entirely by seven SQL triggers, not by Kotlin code. Only backup code reads it.

### 1.2 Why it matters for a usable Kurobayomi (Proposal)

- Every P0 screen (library, reader progress, history, categories, updates) reads or writes this schema. Without it there is no library and no reading progress.
- The schema is the compatibility contract for backups and for importing an existing Aniyomi library. A user who already has a library in Aniyomi can only bring it over through this area's importer (`T-03a-023`, currently P2; see question Q2 in section 4.2).
- Kurobayomi keeps the Aniyomi table, column and trigger names and the schema version 33, so the same file layout works for backup interop with area:21-backup-format-and-create and area:22-backup-restore.

### 1.3 In scope

- Every `CREATE` statement (9 tables, 6 named indexes, 7 triggers, 3 views) as the baseline `schema_v33.sql`.
- Every named statement of the 12 `.sq` files: 74 statements (mangas 18, chapters 11, categories 10, mangas_categories 2, history 8, manga_sync 6, excluded_scanlators 3, extension_repos 8, sources 3, libraryView 1, historyView 2, updatesView 2).
- The 32 migrations: their effects, their data quirks, and an importer that replays them for legacy files.
- The open contract (pragmas, version gate, transactions) and the change-notification mechanism that replaces SQLDelight's query listeners. Repositories and handlers that sit on top belong to area:05 and area:06.

### 1.4 Out of scope (owned elsewhere)

- Repository and mapper code, `data/src/main/java/tachiyomi/data/**` (area:05-data-repos-entries-items, area:06-data-repos-history-track-source-misc). The `AndroidMangaDatabaseHandler` belongs to area:06; area 03 defines what it must guarantee.
- Domain interactors that compute fetch intervals, chapter sorting, chapter sync and category renumbering (area:07, area:08, area:10).
- Anime database (area:04-db-anime-schema-migrations).

## 4. Key design decisions and open questions

### 4.1 Decisions adopted by this area (Proposal)

| ID | Decision | Why |
|---|---|---|
| D1 | Keep the Aniyomi schema shape at version 33 (same table, column and trigger names, same column order), except `history.last_read` is `NOT NULL` | Makes backup interop and the importer simple; `SELECT *` mapping stays positional-safe through name-based mapping |
| D2 | Create a fresh database from the baseline SQL only. Migrations 1..32 are never run on a Kurobayomi file; they exist only in the importer | Matches what Aniyomi produces for new installs; avoids replaying 32 steps with known bugs |
| D3 | Mark Kurobayomi files with `PRAGMA application_id = 0x4B555230` ("KUR0"). Aniyomi files have `application_id = 0`, so an Aniyomi file at any version is refused and routed to the importer | Prevents accidental writes to an Aniyomi file that also has `user_version = 33` (verified in part docs) |
| D4 | Replace SQLDelight with hand-kept SQL constants, one module per `.sq` file, plus conformance tests (`TC-S00` schema listing, `TC-S01` every statement prepares, `TC-S02` query plans) | SQLDelight's compile-time checks have no Rust equivalent; these tests cover the same failures |
| D5 | Use bundled SQLite through `rusqlite` 0.40 (`bundled`, `hooks`, `functions`, `backup`) | The distro SQLite differs in build flags: the bundled build keeps double-quoted string literals enabled, the Arch `sqlite3` CLI disables them (verified). Pin one engine |
| D6 | Rewrite every `IN :list` to `IN (SELECT value FROM json_each(:ids))` | Avoids the 32766 variable limit (E22) |
| D7 | Notify subscribers with SQLite `update_hook` plus `commit_hook` (superset of SQLDelight's table names, includes trigger-driven and cascade writes) | SQLDelight's per-statement table list misses trigger writes (verified in the reactive topic, section 1.2 item 5) |
| D8 | Fix three Aniyomi defects in Kurobayomi (not in the importer): category delete renumbers only user categories (Q7), `%` and `_` in history search are escaped (Q11), Clear database runs in one transaction (Q17). Keep all other quirks verbatim for parity | Each fix is local and does not change stored data shape |
| D9 | The importer never writes into the live file. It builds a new file, copies rows before the trigger half of the baseline is created, and swaps only after confirmation; the old file is renamed `manga.db.bak-<UTC>` and never deleted | Copying through live triggers would bump every `version` and `last_modified_at` |
| D10 | Migration `N.sql` upgrades version `N` to `N+1`; a `VACUUM INTO` backup is taken before the first pending migration and the newest 3 backups are kept | Same numbering as Aniyomi, so `34.sql` continues the same sequence |

### 4.2 Questions for the user (need a decision)

| ID | Question | Recommendation |
|---|---|---|
| Q1 | Must Kurobayomi stay able to exchange backups with Aniyomi or Mihon? | Yes (default in this plan). ### 6.3 Risks

| Risk | Effect | Mitigation |
|---|---|---|
| SQL drift from the Kotlin text during hand-port | Silent behaviour change | TC-S00 (schema listing), TC-S01 (all statements prepare), TC-T matrix (trigger versions), TC-L and TC-H fixtures |
| Notification storms | Library query takes about 250 ms at 5000 favourites and 300000 chapters; each page turn commits | Subscriptions paused when hidden; 300 ms trailing debounce in the UI; conflation (TC-N08); progress buffering in area:43 |
| Imported rows carry Aniyomi defects | Updates feed wrong for legacy rows (migration 10 bug, `date_added` shared) | Importer reports `DateAddedBackfillBug`; no silent repair |
| Concurrency between GTK, tokio and the writer | Deadlock if a write closure waits on the main thread | Writer closures are synchronous and never call GTK (`T-03a-033`; [p1-edge-cases-and-tests.md](p1-edge-cases-and-tests.md) section 3, item 5) |
| Divergence from upstream after 33 | Aniyomi may add migrations after this snapshot | Re-pin the baseline on each upstream change; the migration catalogue is the diff point |
| Unicode case mismatch | Duplicate detection misses non-ASCII titles | P2 `T-03a-025` registers `kuro_lower` |
