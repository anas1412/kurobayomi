# Area 03 / part 1 — Topic: migrations 1..32 (history, exact effects, legacy import)

All paths are repo-relative to `/home/blackbox/aniyomi-src`. Migration files live in `data/src/main/sqldelight/migrations/`. File `N.sqm` upgrades a database whose `PRAGMA user_version` is `N` to `N+1`. The manga database therefore ends at version 33 (`Database.Schema.version`).

## 1. How SQLDelight/Android ran migrations (OBSERVED)

1. `app/src/main/java/eu/kanade/tachiyomi/di/AppModule.kt:78-101` builds `AndroidSqliteDriver(schema = Database.Schema, context = app, name = "tachiyomi.db", factory = RequerySQLiteOpenHelperFactory() (or FrameworkSQLiteOpenHelperFactory() in debug builds on API 30+ so Android Studio's Database Inspector works), callback = AndroidSqliteDriver.Callback(Database.Schema) { onOpen })`.
2. The Android `SupportSQLiteOpenHelper` lifecycle is `onConfigure` -> (`onCreate` for a new file | `onUpgrade(oldVersion, newVersion)` for an older file | `onDowngrade` for a newer file) -> `onOpen`. `onCreate` / `onUpgrade` run inside one transaction. `AndroidSqliteDriver.Callback` maps `onCreate` to `Schema.create(driver)` and `onUpgrade` to `Schema.migrate(driver, oldVersion, newVersion)`, which executes `N.sqm` for each N from `oldVersion` up to `newVersion - 1`, statement by statement.
3. The `onOpen` override of `AppModule.kt:88-100` is the ONLY place pragmas are set, and it runs AFTER create/upgrade, so every migration ran with `foreign_keys` OFF (SQLite's default on Android). The three pragmas it then executes (each via `PRAGMA <x>` + `cursor.moveToFirst()` + `cursor.close()`): `foreign_keys = ON`, `journal_mode = WAL`, `synchronous = NORMAL`.
4. A database newer than 33 raises `onDowngrade`, which the default helper implementation turns into `SQLiteException: Can't downgrade database from version X to Y`. Nothing in the repository catches it.
5. `data/build.gradle.kts` sets `schemaOutputDirectory.set(project.file("./src/main/sqldelight"))` for `Database`; SQLDelight's `verifyMigrations` normally needs `<version>.db` snapshots there; none are committed (`find data/src/main/sqldelight -name '*.db'` is empty), so migration correctness is not machine-checked upstream.

Proposal for Kurobayomi: the baseline (`p1-topic-baseline-schema.md`) is created directly on an empty file; migrations 1..32 are NOT executed on fresh databases. They are embedded only for the legacy importer (`T-03a-022`, `T-03a-023`). Kurobayomi's own future migrations start at `34.sql` and use the same "N upgrades N to N+1" rule.

## 4. Annotation stripping rules for the embedded legacy SQL

The importer embeds `migrations_legacy/1.sql` .. `32.sql`, produced mechanically from the `.sqm` files by these rules (a one-off generator script run by the developer, verified by `T-03a-022`'s test that every produced statement executes):

1. delete lines starting with `import `;
2. delete the tokens `AS Boolean`, `AS Long`, `AS Float`, `AS Date` that appear after a column type (regex `\bAS (Boolean|Long|Float|Date)(?![A-Za-z])`);
3. replace `"System category can't be deleted"` with `'System category can''t be deleted'` and `VALUES (0, "", -1, 0)` with `VALUES (0, '', -1, 0)`;
4. keep everything else byte-for-byte, including SQL comments (lines starting with `--` and block comments delimited by `/**` and `*/`).

Verified: after these rules, migrations 14..32 applied to the reconstructed version-13 state succeed and yield the schema compared in `p1-topic-baseline-schema.md` section 4.

## 5. Importer algorithm (Proposal, `T-03a-023`)

Input: path to an Aniyomi/Mihon-style `tachiyomi.db` (the user can find it in a Syncthing'd or adb-pulled copy of `/data/data/<app id>/databases/`). Output: a new database file that replaces Kurobayomi's `manga.db` only after the user confirms (merging two libraries is out of scope; use the Aniyomi backup format via area:22-backup-restore for merging).

1. Open the source read-only (`SQLITE_OPEN_READ_ONLY`), read `PRAGMA user_version = v`. If `v > 33`: abort with message "This database comes from a newer Aniyomi version". If `v < 14`: abort with "Database too old; open it once in Aniyomi/Mihon first" (versions 1..13 are untested because the version-1 DDL is unavailable; see section 2).
2. Copy the file (plus `-wal` and `-shm` siblings when present) into a temp directory; open the copy read-write; execute `PRAGMA foreign_keys = OFF`.
3. For `n in v..=32`: run embedded `n.sql` inside one `BEGIN IMMEDIATE` / `COMMIT` pair per migration; after migration 15 additionally run `DROP TABLE IF EXISTS history_temp;`.
4. Run `PRAGMA foreign_key_check`; any violating row is deleted for the child table (`DELETE FROM chapters WHERE manga_id NOT IN (SELECT _id FROM mangas)`; `DELETE FROM history WHERE chapter_id NOT IN (SELECT _id FROM chapters)`; `DELETE FROM manga_sync WHERE manga_id NOT IN (SELECT _id FROM mangas)`; `DELETE FROM mangas_categories WHERE manga_id NOT IN (SELECT _id FROM mangas) OR category_id NOT IN (SELECT _id FROM categories)`; `DELETE FROM excluded_scanlators WHERE manga_id NOT IN (SELECT _id FROM mangas)`) and counted in the import report.
5. Build the target: the importer never mutates the user's live `manga.db` in place. It creates a new database file from the baseline script split into two halves (half A = tables, named indexes and the seed row `categories(0, '', -1, 0, 0)`; half B = the 7 triggers and the 3 views).
6. Copy with `ATTACH DATABASE '<migrated copy>' AS src`: for each table in dependency order `categories` (skip `_id = 0`, already seeded), `mangas`, `chapters`, `mangas_categories`, `history`, `manga_sync`, `excluded_scanlators`, `sources`, `extension_repos` run `INSERT INTO main.<t> (<explicit column list>) SELECT <same explicit list> FROM src.<t>` inside one transaction, with `coalesce(last_read, 0)` for `history.last_read`. Only columns present in the baseline are listed, so `mangas_categories.last_modified_at` is dropped naturally. The copy happens BEFORE half B is executed so no trigger fires: copying through live triggers would bump `version` and `last_modified_at` of every row.
7. `PRAGMA user_version = 33` on the target; `ANALYZE`.
8. Report: counts per table, number of dropped orphan rows, source version, and whether quirks (migration 10 `date_added`, `history_temp`) applied.
9. Swap: when the live `manga.db` has at least one row in `mangas`, the UI asks for confirmation (message key `clear_database_confirmation`-style wording is owned by the UI area); on yes the live file is renamed to `manga.db.bak-<UTC yyyyMMddHHmmss>` (never deleted) and the new file is moved into place.
