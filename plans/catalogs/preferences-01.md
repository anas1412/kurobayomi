## 1. How Aniyomi stores a preference (OBSERVED, needed to read the tables)

* Backing store: Android `SharedPreferences` default file, `PreferenceManager.getDefaultSharedPreferences(context)` (`core/common/src/main/java/tachiyomi/core/common/preference/AndroidPreferenceStore.kt:14`). One flat key/value namespace, no sections.
* Primitive kinds (`core/common/src/main/java/tachiyomi/core/common/preference/PreferenceStore.kt`): `getString` (default `""`), `getLong` (0), `getInt` (0), `getFloat` (0f), `getBoolean` (false), `getStringSet` (empty set), `getObject(key, default, serializer, deserializer)` (stored as a String), `getEnum` (extension function: stored as `Enum.name`).
* Read failure rule (`AndroidPreference.kt:29-36`): a `ClassCastException` (stored value has another type) deletes the key and returns the default. Enum rule (`PreferenceStore.kt` `getEnum`): an unknown enum name returns the default silently. Object rule (`AndroidPreference.kt` `Object.read`): missing or any exception returns the default.
* Change notification: every preference exposes `changes()`, a Flow that emits the current value first (`onStart { emit("ignition") }`) and again whenever the key changes; many viewers register on it so settings apply live. A few consumers instead call `.get()` once at construction (noted per key as "read once").
* Three logical stores, distinguished only by a key prefix (`core/common/src/main/java/tachiyomi/core/common/preference/Preference.kt:28-48`):
  * **normal**: no prefix. Included in backups (`PreferenceBackupCreator.createApp`).
  * **app-state**: prefix `__APP_STATE_`. Internal state that is not a user preference. Never written into backups: `PreferenceBackupCreator.kt` `toBackupPreferences()` does `filterKeys { !Preference.isAppState(it) }`.
  * **private**: prefix `__PRIVATE_`. Credentials/tokens. Dropped from backups unless the backup option "Private settings" (`BackupOptions.privateSettings`, default false) is on (`PreferenceBackupCreator.kt` `withPrivatePreferences`).
* Restore rule (`app/src/main/java/eu/kanade/tachiyomi/data/backup/restore/restorers/PreferenceRestorer.kt`): for each backed-up `(key, value)` the value is written only if the currently stored value for that key has the same primitive type (`prefs[key] is Int?`, `is Long?`, `is Float?`, `is String?`, `is Boolean?`, `is Set<*>?`). After restoring app preferences it re-runs `AnimeLibraryUpdateJob.setupTask`, `MangaLibraryUpdateJob.setupTask`, `BackupCreateJob.setupTask` so interval preferences take effect.
* Per-extension preferences are separate SharedPreferences files named `source_<sourceId>` (`source-api/src/commonMain/kotlin/eu/kanade/tachiyomi/animesource/utils/Preferences.kt:13` `preferencesKey(id) = "source_$id"`; `ConfigurableSource.kt:25`, `ConfigurableAnimeSource.kt:25`). They are not in the main namespace.
* One-time key rewrites are done by the migration framework (`app/src/main/java/mihon/core/migration/migrations/*.kt`, run by `Migrator` from `App.kt:166-181`, driven by the app-state key `last_version_code`). Migrations relevant to this chunk are cited per key.

### Proposal: Rust-side conventions used in the "Rust field" column

* Settings file `$XDG_CONFIG_HOME/kurobayomi/settings.toml` (serde, one `Settings` struct with sub-structs named below, every field `#[serde(default)]` so a missing or unknown field never breaks load); app-state values in `$XDG_STATE_HOME/kurobayomi/state.toml`; secrets in the Secret Service keyring (via `oo7`), never in either file. Field spelled `section.field` means `Settings.section.field`. Sections used in this chunk: `ui`, `library`, `reader`, `downloads`, `sources`, `sources.data_saver`, `tracking`, `backup`. area:02-preferences-system owns the final layout; if it renames a section the field names here follow mechanically.
* Enums are Rust enums with `#[serde(rename_all = "SCREAMING_SNAKE_CASE")]` where the Aniyomi enum constant names must round-trip with backups; otherwise snake_case.
* Aniyomi backup import (area:22-backup-restore) reads the legacy key string from the "legacy key" column and converts using the value mapping given in the details; Kurobayomi's own backup export writes the same legacy keys so that Aniyomi can restore them.

### Details: `animelib_sorting_mode`

Constants: `filledRatioLimit = 0.0025`; `THRESHOLD = 0.75`; `thresholdForBlack = (uint8_t)(255.0 * 0.75) = 191` (a pixel counts as "dark" when `pixel < 191`); `thresholdForWhite = (uint8_t)(255.0 - 255.0 * 0.75) = 63` (a pixel counts as "light" when `pixel > 63`). `findBorders` computes `top = findBorderTop`, `bottom = findBorderBottom`, then `left = findBorderLeft(top, bottom)` and `right = findBorderRight(top, bottom)` and returns the rectangle `{x = left, y = top, width = right - left, height = bottom - top}`. Each of the four searches: (1) sample the edge line (first/last row or column; rows are sampled every 2nd pixel in x, columns every 2nd pixel in y over `[top, bottom)`), counting `blackPixels` (`pixel < 191`) and `whitePixels` (`pixel > 63`; the code checks black first with `else if`); limit `filledLimit = round(length * 0.0025 / 2)` where `length` is the image width for top/bottom and image height for left/right (note: `height`, not `bottom - top`); (2) if both counts exceed the limit the edge is mixed, return "no crop" for that side (0 for top/left, full size for bottom/right); (3) otherwise the detector is `isBlackPixel` (content = dark pixels, assumes a light border) unless the dark count exceeds the limit, in which case the detector is `isWhitePixel` (content = light pixels, assumes a dark border); (4) scan inward line by line (starting at index 1 for top/left, at `size - 2` for bottom/right, every 2nd sample along the line) and return the first line whose count of detected pixels exceeds `filledLimit` (`top`/`left` return the index, `bottom`/`right` return index + 1); if none is found return "no crop".

Proposal.
