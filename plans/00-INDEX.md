# Kurobayomi plan: master index

This is the entry point for the complete plan to rewrite Aniyomi (Kotlin / Jetpack Compose, Android) as Kurobayomi, a Rust + GTK4 (gtk4-rs 0.11, no libadwaita) desktop app for Linux. Every path in the plan is repo-relative to the Aniyomi source tree at `/home/blackbox/aniyomi-src` (Apache-2.0), for example `app/src/main/java/eu/kanade/tachiyomi/App.kt`.

The Kurobayomi mockup (UI only) lives at `/home/blackbox/kurobayomi`. The plan documents live in `/home/blackbox/kurobayomi/plans/`.

## What this plan is

- A complete inventory of Aniyomi capabilities, each mapped to one of three outcomes: (a) ported or rewritten in Rust, (b) replaced by a named Linux-native equivalent, or (c) dropped, with the reason and what the user loses.
- Detailed enough for an engineer who never opens the Kotlin: constants, defaults, enum values, bit layouts, SQL semantics, algorithms, ordering rules, edge cases, error handling, message keys, timings and limits.
- Labelling: **OBSERVED** means what the Kotlin does. **Proposal:** means what Kurobayomi should do.
- Task format: `### T-<NN><letter>-<3 digits> — Title` with Priority (P0 to P3), Effort (S, M, L, XL), Depends and Sources. Priorities: P0 is needed for daily reading and watching from one working source. P1 is parity features most users rely on. P2 is long tail and polish. P3 is Android-only or obsolete, with a replacement or drop decision.

## How it was produced

1. **Parallel per-part authors.** Each area folder (`NN-*/`) was written by a separate author working from the Kotlin source. Each folder holds a `00-overview.md`, an inventory, behaviour, Rust design, data and config, edge cases and tests, UI parity where relevant, and a `tasks` file.
2. **Source-derived catalogs.** Source-derived catalogs in `catalogs/` (Android API mapping, network endpoints, preference keys, SQL statements) were extracted from the source tree. `_tools/inventory.py` checks their coverage.
3. **Addenda.** Cross-platform requirements that were missing from the area authors are in `addenda/`.
4. **Synthesis.** Top-level documents (architecture, crate map, data compatibility, decisions, parity, tests, glossary, mockup gap, roadmap) and the milestone files in `milestones/` were written from the area plans. `TASKS.csv` is generated by `_tools/tasks.py export`, which lints every task file (0 errors on the last export).

## User decisions needed

The eleven ADRs are in section 1 of `RISKS-AND-DECISIONS.md`. Summary:

- **ADR-01** Extension strategy: built-in Rust sources first, then WASM (`wasmtime`), `.kuroext` packages. Aniyomi APK extensions stop working.
- **ADR-02** Video backend: libmpv embedded with GL render context. External player is a command template with `$URL`.
- **ADR-03** Torrent engine: `librqbit` by default, TorrServer as fallback.
- **ADR-04** WebKitGTK (`webkit6`) for Cloudflare and login; same user-agent string in WebKitGTK and `reqwest`.
- **ADR-05** Database: `rusqlite` with bundled SQLite; `<data_dir>/anime.db` and the manga database in the same data directory.
- **ADR-06** Backup: Aniyomi-compatible `.tachibk` read and write; Kurobayomi-only settings use the `kuro_` key prefix.
- **ADR-07** Trackers: all ported at P1; Secret Service credential storage.
- **ADR-08** Downloads: `download_slots` honoured; permanent deletion; orphan files kept with a warning.
- **ADR-09** App lock: opt-in, default off, passphrase only, P1.
- **ADR-10** Updates: stable channel only; `update.repo` empty by default; distro packages are the update path.
- **ADR-11** Linux settings scope: disabled settings are greyed out, not hidden; default theme inherits the GTK theme.
