# Area 11: upstream defects and hazards found while reading the migration code

Each item is OBSERVED behaviour in Aniyomi at `versionCode = 132` (`app/build.gradle.kts:22`). "Rust" states what Kurobayomi does about it. Item numbers are referenced from the other area-11 documents.

1. `last_version_code` moved keys at build 113 and the framework treats a missing value as a fresh install.
   `NoAppStateMigration` (`NoAppStateMigration.kt:17-35`) renames `last_version_code` to `__APP_STATE_last_version_code`; `App.initializeMigrator` (`App.kt:169`) reads only the new key. An install that jumps from a build below 113 straight to a current build finds no stored value, so `old == 0`, strategy `Initial`, and all versioned steps are skipped (including steps 113 to 130 that it needed). The same happens after the preference file is cleared. Rust: key `last_version_code` in `state.toml` is never renamed; a future rename must read the old key as a fallback in the same release; a unit test asserts that `old == 0` runs only the always-steps.
2. `TrustExtensionRepositoryMigration` has `version = 7f` (`TrustExtensionRepositoryMigration.kt:14`) although it belongs to the current generation of code (it uses the new `extension_store` table). A step runs only when `old + 1 <= version <= new`, so it runs only for stored values 1 to 6, which no real install has. It is dead code. Rust: not ported as a migration; its conversion is kept as pure functions (T-11a-017).
3. A thrown exception inside any step crashes startup on every launch. The failing `async` cancels the plain `Job()` of `Migrator.scope` (`Migrator.kt:13`); the exception reaches the global uncaught handler; `last_version_code` is never stored; the same range reruns next launch and hits the same exception, so the user is stuck in a crash loop until a new build. Steps that already ran are not rolled back. Rust: the runner returns `Err`, writes nothing and shows the crash dialog, whose text names the failing migration and tells the user to start once with `kurobayomi --skip-migrations`, which stores the new version code without running anything (T-11a-027; the flag has no task yet, see 00-overview.md section 4). Each migration must be idempotent.
4. `MigrateRotationViewerValuesMigration` (60) writes `pref_default_orientation_type_key` and `pref_default_reading_mode_key` unconditionally, with the reading mode defaulting to `1` (left to right) when the old viewer key is absent, although the current default is right to left (`flagValue 2`, `ReaderPreferences.kt:38-41`). A rerun (after a later step crashed) overwrites the user's current choices with `1` and `FREE (0x08)`. Rust: write only when the legacy key exists (T-11a-013).
5. `RemoveReaderTapMigration` (77) defaults `reader_tap` to `false` (`RemoveReaderTapMigration.kt:18`), so an absent key disables tap navigation (`navigationModePager = navigationModeWebtoon = 5` = disabled layout) for users who never touched it. Rust: the normaliser converts only when the key is present; when absent it leaves the navigation preference alone, which is the safer choice for imported backups.
6. `MigrateToTriStateMigration` (52) writes an Int under today's `pref_filter_library_*_v2` enum keys (`MigrateToTriStateMigration.kt:21-37`). Those keys hold an enum name String; the Int fails the typed read, `Object.read` catches the exception and returns `DISABLED`, and nothing deletes the bad value. Pre-52 filters are lost. Rust: the normaliser writes the enum name (T-11a-011).
7. Anime library sort is lost by steps 64 and 81. Step 64 emits `LAST_CHECKED`, `UNSEEN`, `DATE_FETCHED`; step 81 turns `LAST_CHECKED` into `LAST_MANGA_UPDATE` and `DATE_FETCHED` into `CHAPTER_FETCH_DATE` for anime too (`RenameEnumMigration.kt:31-41`), but the anime deserializer expects `LAST_ANIME_UPDATE`, `UNSEEN_COUNT`, `EPISODE_FETCH_DATE` (`domain/src/main/java/tachiyomi/domain/library/anime/model/AnimeLibrarySortMode.kt`), so `Type.Alphabetical` is used for those and for any unknown name. Only `ALPHABETICAL`, `LAST_SEEN`, `TOTAL_EPISODES`, `LATEST_EPISODE`, `DATE_ADDED` survive. Rust: the normaliser uses the correct anime names (T-11a-011).
8. `MigrateTriStateMigration` (99) converts `pref_filter_library_unseen`, `pref_filter_library_started`, `pref_filter_library_bookmarked`, `pref_filter_library_completed` and `pref_filter_library_tracked_<id>` (the 11 tracker ids) into `pref_filter_library_*_v2` keys (`MigrateTriStateMigration.kt:23-31`), while the anime library reads `pref_filter_animelib_*_v2` (`LibraryPreferences.kt:110-143`), so no anime filter is migrated and the anime-only keys (`pref_filter_library_unseen_v2`) are never read. Rust: the normaliser maps every legacy key into the correct media-type family explicitly (T-11a-011).
9. `VideoOrientationMigration` (127) reads an unset orientation as `10` (`FULL_SENSOR`) and writes `Free` (`VideoOrientationMigration.kt:23-44`), replacing the current default `SensorLandscape` for everyone who never changed the setting. Rust: orientation has no desktop meaning; the normaliser writes only when the key is present.
10. `MovePlayerPreferencesMigration` (93) rewrites the whole `tracking_queue` file inside the per-preference loop and destructures `split(":")` into two parts (`MovePlayerPreferencesMigration.kt:37-45`). The current store writes bare Floats (`DelayedMangaTrackingStore.kt:18-23`), so a value like `5.0` throws `IndexOutOfBoundsException`; the loop also runs once per set preference. Rust: dropped (T-11a-024).
11. `EnumsMigration` (123) uses `Debanding.entries.first { it.ordinal == value }` and `VideoAspect.entries.first { ... }` (`EnumsMigration.kt:34-35`), which throw `NoSuchElementException` for ordinals above 2, and a rerun resets debanding/aspect/gpu-next to defaults because the old keys are gone. Rust: out-of-range ordinals fall back to defaults (T-11a-014).
12. `DeleteMangaCategory` builds its list of category preference sets with `libraryPreferences.mangaUpdateCategories()` twice and never `mangaUpdateCategoriesExclude()` (`domain/src/main/java/tachiyomi/domain/category/manga/interactor/DeleteMangaCategory.kt:35-41`), so the manga "exclude from update" set keeps dangling ids after a category is deleted (`DeleteAnimeCategory.kt:36-42` is correct). `CategoryPreferencesCleanupMigration` (129) was added to repair these leftovers; nothing repairs them after build 129. Rust: one shared `prune_dangling_category_ids` helper is used by category deletion for both media types and for all preference sets of each (T-11a-008); area:08-domain-library-category-history-updates calls it.
13. `ExternalRepoMigration` (114) wraps every entry in `https://raw.githubusercontent.com/$repo/repo`, including entries that are already URLs, so it is not idempotent (`ExternalRepoMigration.kt:15-17`). Rust: wrap only non-URL entries (T-11a-017).
14. Steps 52, 60, 99, 120, 123, 127 write their outputs unconditionally from defaults when the old key is absent, so rerunning them (or running them on a profile that already has new values but a stale version counter) overwrites user choices. Rust: every normaliser rule is "if the legacy key is present, convert" and never writes defaults.
15. In `LibraryPreferences` the manga and anime chapter/episode "display by name or number" preferences share one key string (`default_chapter_display_by_name_or_number`, lines 205-212) and the sort-direction preferences share `default_chapter_sort_by_ascending_or_descending` (lines 215-222), so changing either media type's default changes both; `MoveChapterPreferencesMigration` visits those two keys twice (`MoveChapterPreferencesMigration.kt:19-32`). Rust: area:02-preferences-system decides the key layout; the normaliser reads the shared key once and applies it to both.
16. Iteration order of the repository sets in step 7 is the `HashSet` order of `SharedPreferences.getStringSet`, so the generated placeholder names `Repo #N` and fingerprints `NOFINGERPRINT-N` depend on the hash order (`TrustExtensionRepositoryMigration.kt:20,34`). Rust: sort the URLs lexicographically before numbering so imports are reproducible (T-11a-017).
17. `NoAppStateMigration` (113) moves `library_unseen_updates_count` to an app-state key, but `LibraryPreferences.newAnimeUpdatesCount()` still reads the un-prefixed key (`LibraryPreferences.kt:149`). The counter is therefore reset to 0 by the move. Rust: the counter is app state in `state.toml` from day one.
18. The migration chain executes on the main thread inside `App.onCreate` (the `UNDISPATCHED` start plus no suspension points), and `MainActivity` additionally blocks with `runBlocking` (`MainActivity.kt:166`). A slow step delays the first frame; there is no progress UI. Rust: `run_blocking` runs before the window exists and a spinner appears only when the run exceeds 300 ms (T-01a-043).
19. `MigrationJobFactory` dry-run seeds the fold with `CompletableDeferred(true)` and returns `true` for every element, so even a dry run triggers the completion listener that persists the new version code. No caller uses dry run, but a harness that did would store the version. Rust: `run` returns `Ok(true)` for a dry run as Kotlin does, but `run_blocking` never accepts `dry_run = true`, and the completion callback stores the code only when `!ctx.dry_run`.
20. `Migrations.kt` exposes `migrations` as a getter that allocates 44 new objects per access (`Migrations.kt:5-6`). Harmless; Rust uses a `static` slice.
