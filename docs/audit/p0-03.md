## Short summary

The crates are in good shape: almost every task has an implementation and tests named after the acceptance bullets. The weak spot is the wiring into the app window. Four patterns repeat.

1. **Parallel implementations in `src/`.** The reader (`src/reader/page_decode.rs`, `page_transform.rs`, `loader/http.rs`, `rules.rs`, `source_pages.rs`) and the local-folder flow (`src/local_flow/`, `src/local_flow_anime/`) re-implement what `kuro-core`, `kuro-local` and `kuro-source` already have. The crate versions then have no caller (image decode, wide-image check, animated check, filename sanitiser, page state machine, image fetch with progress, `LocalMangaSource`, `LocalAnimeSource`, roots, safe_join).
2. **The local source is not a source.** The Aniyomi design (a `local` folder under the storage base, listed in Browse as source id 0 with popular, latest and search) is not built into the app. The app has a different flow: "Add local manga folder" and "Add local anime folder" in the library menu scan one folder into library rows. `LocalMangaSource` and `LocalAnimeSource` are never constructed outside `kuro-local` tests (rg over `src/` and `crates/`). Nothing is wrong with the flow, but the Browse listing, sort options, roots, season detection, playback hoster and path-safe URL tasks are crate-only.
3. **Mockup builders are still the fallback** for the Browse and search pages (`src/entry.rs`). Details are in the "Placeholders" section below, because the user asked about it.
4. **Defects found while tracing** (each is in the table with file and line):
   - The cookie jar is loaded as separate in-memory copies (built-in sources client, recipe client, plus a fresh copy in each settings action), so Clear cookies, cookie import and "clear extension cookies" act on a copy and not on the jar the running clients hold.
   - The network client is built with a toast feed that is dropped at once (`src/net_client.rs:13`), so every toast the network stack raises (Cloudflare, clear cookies) is lost.
   - The live chapter sync still widens `f32` to `f64` (`kuro-domain/src/items/chapter_sync.rs:72` and `:96`), so `1.1` is stored as `1.100000023841858`. The corrected helper `domain_chapter_number` exists and has no caller.
   - Three separate `MangaSyncLocks::default()` instances (`src/entry_core/backend.rs:135`, `src/misc/runner.rs:288`, migration), so a manual refresh and a library update of the same manga are not serialised.
   - In the local manga scan, a corrupt archive or EPUB as the lowest chapter fails the whole folder (`src/local_flow/scan.rs:71`, `cover_of(...)?`), against deviation E-MANGA-3. `kuro-local` swallows that error; the app scan does not call that code.
   - `kuro-source` depends on `reqwest` through its torrent lookup (`crates/kuro-source/Cargo.toml:17`), against T-15a-001.
   - `getNameForMangaInfo` (`kuro_source::name_for_manga_info`) is never called; the entry page always shows `Name (LANG)` (`src/entry_core/backend.rs:174`).
   - Two filename sanitisers disagree on reserved names (`CON` gives `_CON` in `kuro_core::storage::valid_filename`, `CON_` in `kuro_core::text::build_valid_filename`, which is what the downloads crate calls), and the reader save path (`src/reader/rules.rs:60`) has neither the reserved-name rule nor the 240-unit cap.
