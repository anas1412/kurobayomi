What is solid: the database crates (kuro-db, kuro-data) and the preference crate (kuro-prefs). Schemas, pragmas, triggers, statements, views, change notification, repositories and the preference store all exist with many tests and are reached by the live screens. The weak area is area 01a (app bootstrap): the plan's startup design was never built as written.

Main findings:

1. **No AppContext exists** (T-01a-003, -017, -018). Services are reached through `data::app()` (a thread_local with only 2 databases, 2 category services, 3 pref sections: `src/data.rs:25`) and `shell::Shell` (`src/shell/host.rs:17`). There is no accessor table, no `Unimplemented` stubs, and no post-first-frame warm-up. Everything else in the app builds its own client, image service or pref sections ad hoc (for example `src/browse/builtin.rs:246-258` builds its own HTTP client and `ImageService`).
2. **Two migrators, the plan's one is not called.** `kuro_core::migrate` (Version, Strategy, plan, run, run_blocking, three Always steps) is tested but nothing in `src/` calls it. What runs at startup is `kuro_prefs::migrate::migrate` (`src/data.rs:73`), whose list is empty. It never writes `last_version_code` on a first install (`crates/kuro-prefs/src/migrate.rs:~60`: an empty plan returns before storing), so `Updating last version to` never logs.
3. **`Prefs::open` is never called.** `src/data.rs` opens the store with `settings_load::open` and builds sections one by one. `Prefs::repair()` (startup repair of invalid enum values) therefore never runs in the app. The settings screens build `Prefs::with_store(.., MemorySecrets)` (`src/settings_ui/route.rs:56`). `Prefs` has 13 sections, not 18. Several helper functions in kuro-prefs have no caller: `mpv_decoder_options`, `should_mark_seen`, `http_log_level`.
4. **Fabricated placeholder pages are still reachable** (T-03a-034, T-05a-026). `screens::body("global_search")` first asks `browse::search_screen::body`, which returns `None` unless a search intent, a parked route or an entry hand-off exists (`src/browse/search_screen.rs:366-385`). A plain open of Global search then falls to `entry::global_search` (`src/entry.rs:657`): "Source A/B/C", a progress bar fixed at 0.6, "No results found". `tracker_search` (`src/entry.rs:764`) is all `title_n(i)` rows, "Author name", fixed scores. Download queue (`src/screens.rs:432`) is always the empty state with a hard-coded Stopped subtitle (`src/screens.rs:386`). The same fallback shape exists for `updates()`, `history()`, `library()` and `browse` (`src/screens.rs:22-26,236`), though those only trigger when the data or the live page fails to start. `screens.rs:40-46` opens the reader and player with the literal titles "Title 1".
5. **Three copies of the item-name sanitizer.** The tested one (`kuro_data::sanitize::sanitize_item_name`) has no caller. Chapter and episode sync use `kuro_domain::items::source_sync::sanitize_chapter_name` (`name.trim()`, Rust whitespace rules), which differs on U+001C to U+001F and U+0085. A third copy is `kuro_db::episode_sanitizer`.
6. **Blocking database calls on the GTK thread.** The async `read_async`/`write_async` exist, but the synchronous `Db::read`/`write` run on the caller and the GUI uses them in `src/library/actions.rs:461,514,543`, `src/settings.rs`, `src/browse/migrate_live.rs`. The plan says these run through `spawn_blocking`.
7. **Theme mode** has three apply paths (`src/theme/apply.rs:195`, `src/settings_ui/appearance.rs:63`, `src/pref_model/widgets/theme_mode.rs:30`). The live one writes the portal value for SYSTEM instead of restoring the startup value, which is what the plan forbids ("never forces light for SYSTEM").
8. **Crash handling is mostly done now** (the older FINDINGS.md rows for spawn, contain, prune are stale: `crate::crash` has spawn, `contain`, `prune`, and child-process tests for thread, tokio, spawn_blocking, nested panic and main thread). Gaps: `contain` has no caller while four crates use `catch_unwind` directly, and the reporter window has no test.
